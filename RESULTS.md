# PolarFire Vibration Monitor - software model results

All numbers below are generated by `run_experiments.py` -> `results.json` -> `make_results_md.py`. **Everything is simulation on synthetic data. No hardware was touched and no PolarFire resource/power/timing figure in this file is measured.**

## 2. Synthetic data: assumptions (all invented, none fitted to a real machine)

- Sampling: fs = 8192 Hz, window N = 4096 (0.5 s), 32 accelerometers at 0-3 m along a machine train, +-8 g full scale, 12-bit ADC (3.9 mg/LSB), stored as int16 codes.
- Shaft speed 20-38 Hz (1200-2280 rpm), per-window; within the window: linear ramp (+-2% total), sinusoidal wobble (0.2-2% at 0.2-2 Hz). A tacho speed estimate with 0.3% (1 sigma) error is assumed available and is used to place the order bands.
- Bearing: 6205-like geometry (9 balls, d = 7.94 mm, D = 39.04 mm, 0 deg contact). Orders: BPFO = 3.585X, BPFI = 5.415X (BSF 2.357X, FTF 0.398X in the code docstring only; BSF/FTF faults are not generated). Impulses at BPFO/BPFI with 1% slip jitter excite a resonance (2.3-3.1 kHz, tau 0.4-1.0 ms); inner race is amplitude-modulated at 1X (depth 0.5-1.0), outer race is not.
- Imbalance: 1X dominant (+ small 2X). Misalignment: 2X dominant with 1X, 3X, 4X. Looseness: 0.5X/1.5X/2.5X sub-harmonics, many harmonics, plus clipping distortion of 1X. Fault severity uniform in [0.3, 1.0] (nominal set). Exactly one fault class per window (no combined faults).
- Background (all classes): residual 1X/2X/3X, white noise (sigma 0.03-0.12 g per window, +-20% per channel) plus a pink-ish component, 30% of windows get a 50 Hz mains pickup (this lies close to 2X for ~25 Hz shafts - a deliberate confounder), 30% get a non-synchronous 150-400 Hz tone, 15% get benign random impacts (raises kurtosis without a bearing fault).
- Coupling: each source reaches channel c with gain exp(-|pos_c - pos_src|/lambda) x U(0.4,1) and 0-3 samples of delay (lambda 0.7-1.8 m depending on source) plus adjacent-channel electrical crosstalk up to 3%.
- Sensor faults per channel per window: gain error +-7%, DC offset +-0.1 g, strong drift ramp (p = 3%, up to 1 g across the window), dropout (p = 2%: 60% flat-line, 40% burst of 5-40% of the window).
- Data sets (distinct RNG seeds, same generator => optimistic relative to reality): train 2550 (+450 validation), `test_nominal` 1200, `test_highnoise` (noise x2.5) 600, `test_heavydrop` (p_drop 15%, p_drift 10%) 600, `test_weakfault` (severity 0.1-0.4) 600. Classes are balanced.
- Known geometry coincidence: 3 x BPFO = 10.75 X is within 1% of 2 x BPFI = 10.83 X, so outer-race harmonics fall inside the 2xBPFI envelope band (visible in `figures/generator_examples.png`). This is a property of the bearing, not a bug.

## 3. Features (448 per window = 32 channels x 14)

Per channel: [0] log2(sum x^2); [1] kurtosis; [2] crest factor; [3-7] log2 band energy at 0.5X, 1X, 2X, 3X, 4-10X (+-0.15X bands, FFT of /4-decimated signal, 2 Hz bins); [8] log2 band energy 10.5X..1 kHz; [9-12] log2 envelope-spectrum energy at BPFO, 2BPFO, BPFI, 2BPFI (2-3.5 kHz 31-tap band-pass -> abs -> /8 boxcar -> 512-pt FFT, 2 Hz bins, band half-width max(3 Hz, 5%); [13] log2 total envelope-spectrum energy.

Fixed-point choices: Q15 31-tap FIR coefficients, Q15 Hann window, radix-2 FFT with Q15 twiddles, >>1 per stage, int16 saturation, guard shifts of 4 (raw) / 5 (envelope) bits, int64 accumulators, Mitchell-style log2 with 4 fractional bits (leading-one detect + linear mantissa). RMS/kurtosis/crest use a float sqrt/divide of integer sums (a hardware divider/sqrt is not modelled).

## 5. Approximate multipliers in the MAC

Operands are int8 in sign-magnitude; the multiplier core acts on 7-bit magnitudes (|x| <= 127); sign handling, accumulation (exact int) and requantisation are exact in all configurations. Approximation is applied to every multiply in all three layers (column `L1 only` = first layer only). Error metrics are exhaustive over all 128x128 magnitude pairs with a *uniform* operand distribution (not the network's actual distribution).

**Cost proxy (NOT synthesis, NOT PolarFire LUTs).** Gate equivalents with assumed unit costs AND=1, FA=5, 2:1 MUX=2.5, FF=6, leading-one detector = 2 GE/bit. Array multiplier = (#partial-product ANDs) + 5 x (#pp bits - #output columns); truncation removes partial-product bits and columns; DRUM = 2 LOD + 2 window shifters + k x k array + shift-amount adder + output shifter; Mitchell = 2 LOD + 2 normalising shifters + log adder + antilog shifter. `MAC GE` adds a 24-bit accumulator (24 x (FA+FF)). Sign logic is omitted for all designs. The constants are textbook-order guesses; only the relative ordering is meant to be informative, and FPGA LUT-based implementations may rank designs very differently (on PolarFire, 8x8 multiplies are likely to map to hard math blocks, where truncation saves nothing).

Because differences of up to ~1 point are inside the sampling CI, **membership of the front for designs near 97% is not statistically meaningful**; only the trend (accuracy falls clearly only for MRED >~ 0.25) is. `drum1` and `mitch0` are the same function (floor to a power of two).

Observations (data, not claims about hardware):
- On this proxy at 7-bit magnitudes, truncation is the only family that reduces GE meaningfully (trunc6: 0.57x multiplier GE at MRED 0.090). DRUM and Mitchell need leading-one detectors and shifters whose proxy cost is comparable to or larger than a 7x7 array: DRUM-4 is 1.00x, Mitchell F=3 is 1.07x. They are expected to pay off at wider operands; that was not tested here (int16 approximate inference was not run because a 2^15 x 2^15 LUT is infeasible).
- Accuracy is very tolerant: even trunc7 (MRED 0.23) stays within about 1 point on the nominal set, while trunc8 (MRED 0.51) loses about 2 points and `weakfault` / `highnoise` degrade first. A plausible but untested explanation is that errors average out over 448-term sums and that Mitchell's one-sided (negative) bias is largely absorbed by the next layer's requantisation.
- No approximation-aware retraining or fine-tuning was done; all models are exact-trained then post-training quantised.

## 6. Workload counts (raw arithmetic, per 0.5 s window; not measured)

- Front end: FIR MACs 5,079,040; FFT butterflies 237,568 (~950,272 real multiplies at 4 per butterfly).
- Neural network: 30,912 MACs = 0.51% of all multiplies in the pipeline. With 32 MAC lanes (one per neuron, output-stationary), layer-by-layer: 992 cycles per inference.
- Consequence: approximating only the NN multipliers can change at most ~0.5% of the multiplications of the whole system; the front end (FIR/FFT) dominates the arithmetic. Approximating the front end was not evaluated.

## 7. RTL skeleton and testbench

`rtl/approx_mul.v` (MODE 0 exact, 1 truncated K, 2 DRUM-K; sign-magnitude, operands in [-127,127]) and `rtl/mac_array.v` (LANES parallel MACs sharing a broadcast activation; acc <= (clear ? bias : acc) + x*w; 24-bit accumulators). `rtl/tb_mac_array.v` is self-checking: (1) exhaustive 255x255 check of exact/trunc4/trunc6/drum4/drum3 against golden values produced by `approx.py`; (2) 12 dot-product trials (8 lanes x 64 elements; trial 0 is a real slice of the quantised layer-0 weights and a real input row) for exact/trunc4/drum4. Golden vectors: `python3 rtl/gen_vectors.py`. Mitchell is not implemented in RTL. The RTL has no reset-less pipeline, no saturation, no layer sequencing/weight memory and no feature front end; it is a skeleton.

Simulation status: SIMULATED with Icarus Verilog 12.0 (`iverilog -g2005`): `TB PASS: 325161 checks, 0 errors` (325125 multiplier checks = 65025 operand pairs x 5 designs, plus 36 dot-product accumulator checks). A mutation of the truncation compensation constant made the same testbench report `TB FAIL ... 129044 errors`, so the checks are sensitive. Log: `rtl/sim.log`. This verifies RTL == Python models only; it is not a timing, power or PolarFire result. Generic yosys `synth` cell counts for the 8-lane array (technology-independent gates, NOT PolarFire LUTs/blocks, not a measurement of resource use): exact 4883, trunc6 4055, drum4 6279 cells. Reproduce: `cd rtl && ./run_sim.sh`.

## 8. Honest caveats

- All data are synthetic and produced by the same generator for train and test; accuracy figures say nothing about real machines. Real vibration has non-stationary loads, gear-mesh, structural resonances, unknown geometry and sensor mounting effects not modelled here.
- Only 3 training seeds on one dataset; no confidence interval over datasets. The test sets are 600-1200 windows, so +-1 to +-3 points is sampling noise.
- The GE numbers are a transparent proxy and were not synthesised; PolarFire (LUT4 / hard multiplier / math-block) cost and power are NOT measured and may differ qualitatively.
- The tacho speed estimate is assumed to exist (order bands depend on it). No speed estimation from the vibration is modelled.
- No combined faults, no fault progression, no unseen-fault detection, no false-alarm rate analysis.
- Hardware, FPGA tools and real sensors were not used.

## 9. Numbers for the proposal (raw numbers and reasoning only; no proposal prose)

Raw numbers
- Channels 32; fs 8192 Hz; window 4096 samples = 0.5 s; ADC 12 bit; classes 6; features/window 448.
- Network 448-64-32-6: 31,014 parameters; 30,912 MACs/inference; int8 weights ~30.3 KiB (+ int32 biases).
- Nominal accuracy (synthetic, n=1200): float 97.03%, int8 97.11%, int16 97.03% (sampling CI about +-1 point).
- Stress sets (n=600 each, int8): noise x2.5 -> 77.11%; 15% channel dropout -> 90.44%; weak faults -> 82.06%.
- Approximate multiplier examples (nominal acc; rel. multiplier GE proxy): exact 97.11% / 1.00; trunc4 97.03% / 0.82; trunc6 96.86% / 0.57; trunc7 96.56% / 0.41; trunc8 94.97% / 0.24; drum4 97.08% / 1.00; drum3 96.72% / 0.98; mitch3 97.17% / 1.07.
- 32-lane MAC array, GE proxy (32 x MAC GE): exact 15616; trunc6 12544; trunc7 11360.
- Cycles per inference with 32 lanes: 992 (arithmetic only; at an assumed 100 MHz that would be 9.9 us - a hypothetical, not a measured clock).
- Front end per window: 5,079,040 FIR MACs + ~950,272 FFT multiplies; NN is 0.51% of multiplies. A single multiplier at 100 MHz (assumed) would need ~61 ms of the 500 ms window.

Reasoning (for your own wording)
- Accuracy is insensitive to multiplier error up to roughly MRED 0.1-0.25 on this synthetic task, so there is room to approximate; the nominal-set CI (about +-1 point) is larger than the observed loss for designs up to trunc7.
- Under the GE proxy only truncation saves area at 7-bit magnitudes; DRUM/Mitchell overheads (LOD, shifters) cancel the saving at this width. Whether this holds on PolarFire fabric is unmeasured and must be checked with synthesis.
- The NN is a tiny share of the pipeline's multiplies, so any system-level saving from approximating it alone is bounded by that share; the proposal's claim has to be scoped accordingly or the front end must be included in the approximation study.
- Bounds on what is claimable: synthetic data only, one dataset, 3 seeds, no hardware measurement.
